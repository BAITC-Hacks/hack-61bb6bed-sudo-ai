# Контракт backend v1

Базовый путь: `/api/v1`. Источник точных JSON-схем — `/openapi.json` и `/docs`.
На защищённых ручках используется cookie `sana_session`. Для изменяющих запросов
передавайте `X-CSRF-Token` из cookie `sana_csrf`. `X-Demo-User` доступен только
в явно включённом локальном demo-режиме; по умолчанию он выключен.
Роль берётся из БД, принадлежность задачи и членство команды проверяются сервером.

| Метод | Путь | Доступ / назначение |
|---|---|---|

Списки задач, откликов и рекомендаций используют `limit` (1–100, default 20),
`offset` (от 0). Ответ: `{ "items": [...], "total": 10, "limit": 20, "offset": 0 }`.
Каталог: `sort=quality|newest`, `skill=python`, `q=текст`. В рекомендациях matching считается
для текущей страницы каталога; это ещё не глобальное ранжирование по релевантности.

## Пример ручного сценария

Перед сценарием зарегистрируйте бизнес и студента в отдельных сессиях.
Студент создаёт команду через `POST /teams`; в отклике используйте её UUID.

1. `POST /tasks/draft`: `{"raw_text":"Нужно автоматизировать 500 обращений в день."}`.
2. `POST /tasks/{id}/analyze`: текущая карточка и `assessment` с баллами,
   причинами, `missing_fields`, максимум тремя `next_questions`, `source` и `warning`.
3. `PATCH /tasks/{id}` принимает поля карточки на верхнем уровне:

```json
{
  "title": "Классификация обращений",
  "problem": "500 заявок ежедневно сортируются вручную",
  "goal": "Сократить время ручной сортировки",
  "deliverable": "REST API классификации и отчёт с метриками",
  "success_criteria": "Точность не менее 80% на тестовой выборке",
  "timeline": "3 недели",
  "skill_slugs": ["python", "llm"],
  "expected_revision": 2
}
```

`expected_revision` необязателен; используйте последнее значение из ответа,
чтобы не затереть изменения из другой вкладки. `null` запрещён; поле можно
очистить пустой строкой. Неизвестные поля/навыки отклоняются.
Чтение возвращает поля карточки в объекте `brief`.

4. Интервью: `POST /tasks/{id}/answer` с
   `{"field":"success_criteria","answer":"Точность не менее 90% на 100 примерах"}`.
   Ответ сохраняется до обращения к AI; при сбое остаётся доступен.
5. `POST /tasks/{id}/analyze` после остальных ручных правок; затем `/publish`.
6. Студент вызывает `/tasks`, затем `/tasks/{id}/apply`:

```json
{
  "team_id": "55555555-5555-4555-8555-555555555555",
  "pitch": "У команды есть опыт классификации текста",
  "approach": "Подготовим baseline, сравним метрики и завернём модель в API",
  "timeline": "3 недели"
}
```

7. Бизнес читает `/business/tasks/{id}/proposals` и вызывает `/proposals/{id}/select`.

## Правила и консистентность

- Состояния задачи: `draft → published → team_selected`.
- Отклики: `submitted → selected | rejected`.
- Публикация требует title, problem, goal, deliverable, success_criteria, timeline
  и оценки текущей версии. Минимального общего балла нет.
- Повторная публикация опубликованной задачи и повторный выбор того же победителя
  идемпотентны. Выбор другой команды после завершения возвращает 409.
- Один отклик `(task_id, team_id)` обеспечен UNIQUE в PostgreSQL.
- Частичный UNIQUE запрещает два `selected` у одной задачи.
- Подача отклика и выбор блокируют одну строку задачи (`FOR UPDATE`). Выбор,
  отклонение остальных и изменение статуса задачи коммитятся вместе.
- AI вызывается между двумя короткими транзакциями. Изменившаяся `revision`
  приводит к 409, ответ AI не применяется. Повторный analyze уже оценённой
  OpenAI версии возвращает сохранённый результат, экономя запрос.
- Публичные карточки не содержат `raw_text`, историю интервью и приватный feedback.
- Все данные основного сценария хранятся в PostgreSQL; SQLite не используется.

## Модель БД

`users`, `teams`, `team_members`, `skills`, `team_skills`, `tasks`, `task_skills`,
`proposals`, `interview_answers`, `task_score_history`, `auth_sessions`,
`team_invites`, `rate_limits`. Пароли хешируются Argon2id; токены сессий
и приглашений хранятся только в виде SHA-256-хешей.
Текущий snapshot оценки хранится в `tasks.assessment_json`; неизменяемая история
в `task_score_history.feedback` содержит все 9 оценок и их объяснения.
Так мы объединяем предложенные в исходном файле `task_scores` и историю в одну
историческую таблицу. Карточка хранится обычными колонками; связи навыков нормализованы.
Таблица `matches` пока не нужна: простой matching вычисляется при чтении;
хранение embeddings и их версий добавится вместе с NVIDIA.

## Ошибки

```json
{"error":{"code":"analysis_required","message":"Проанализируйте текущую версию карточки."}}
```

401 — нет действующей сессии; 403 — чужая задача/команда или неверная роль;
404 — объект отсутствует или черновик закрыт для читателя; 409 — конфликт
состояния/версии/дубликат; 422 — некорректный ввод/неполная карточка;
429 — превышен лимит попыток; 503 — недоступна БД. SQL, ключи и внутренние исключения не выдаются клиенту.
